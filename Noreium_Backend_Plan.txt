NOREIUM — BACKEND DEVELOPMENT PLAN
================================

Project Goal
------------
Noreium is a personal developer environment management system. It stores development tools, APIs, websites, resources, and secrets in one place, groups them into collections/environments, and generates platform-specific setup scripts or checklists.

Core backend goal for MVP:
1. Authenticate a user.
2. Store and manage library items.
3. Group library items into collections.
4. Generate Windows/Linux setup scripts from collections.

Architecture
------------
Use a modular layered architecture:

Request
  -> Route
  -> Middleware
  -> Controller
  -> Service
  -> Repository
  -> Mongoose Model
  -> MongoDB

Responsibilities:

Routes:
- Define HTTP methods and paths.
- Attach middleware.
- Never contain business logic.

Middleware:
- Authentication.
- Authorization.
- Request validation.
- Centralized error handling.
- Optional logging/rate limiting later.

Controllers:
- Receive HTTP requests.
- Read params/query/body/user.
- Call the relevant service.
- Return HTTP responses.
- Do not contain business rules.
- Do not perform direct database queries.

Services:
- Contain application/business logic.
- Validate ownership rules through repositories.
- Coordinate multiple repositories when needed.
- Implement collection/item rules.
- Coordinate script generation.

Repositories:
- Contain Mongoose/database operations.
- Hide database implementation from services.
- No HTTP logic.
- No request/response handling.

Models:
- Define MongoDB document schemas.
- Add indexes, defaults, constraints, and timestamps.

Important:
The feature should be called "library-items", not simply "library", because the stored entity is a LibraryItem. "Library" is the product area; "LibraryItem" is the domain entity.

Core Domain Entities
--------------------
MVP entities:

1. User
2. LibraryItem
3. Collection

Future entity:
4. Secret

LibraryItem is the central Noreium entity.

LibraryItem types:
- TOOL
- API
- WEBSITE
- RESOURCE

Do NOT initially create separate Tool, Api, Website, and Resource models. Use one LibraryItem model with a type field and type-specific metadata.

Relationships
-------------
User
  -> owns many LibraryItems
  -> owns many Collections
  -> later owns many Secrets

Collection
  -> belongs to one User
  -> contains many LibraryItems

LibraryItem
  -> belongs to one User
  -> can belong to many Collections

For MongoDB MVP, keep collection membership inside Collection as an array of LibraryItem ObjectIds instead of creating a separate CollectionItem collection.

Authentication Plan
-------------------
MVP:
- Register
- Login
- Logout
- Get current user

Authentication flow:
1. User registers.
2. Password is hashed.
3. User is stored.
4. User logs in.
5. Server issues authenticated session/token.
6. Protected routes require authentication.
7. User identity is attached to request.
8. Services use the authenticated user ID for ownership checks.

Authorization:
- USER: manage own data.
- ADMIN: platform-level management later.

Do not implement complicated permissions in V1. The primary authorization rule is ownership.

Ownership Security
------------------
Every user-owned query should be scoped to the authenticated owner.

Correct pattern:
- find item by item ID AND owner ID
- update item by item ID AND owner ID
- delete item by item ID AND owner ID
- find collection by collection ID AND owner ID

Never assume that knowing an ObjectId grants access.

A user must never be able to read or modify another user's library items or collections by changing an ID in a request.

Library Item API Behavior
-------------------------
Create:
Input:
- type
- name
- description
- url
- tags
- metadata

Server adds:
- ownerId
- timestamps

Validation:
- type must be supported.
- name must be present and within limits.
- URL must be valid when supplied.
- metadata must be an object.
- tags must be an array of strings.

Read:
- Return only the authenticated user's items.
- Support filters later:
  - type
  - tags
  - search
  - pagination

Update:
- Do not allow client to change ownerId.
- Do not allow client to change protected system fields.
- Validate updated values.

Delete:
- Confirm ownership.
- Delete the item.
- Decide later whether references in collections should also be cleaned automatically.

Collection API Behavior
-----------------------
Create collection:
- name
- description

The server sets ownerId from authenticated user.

Add item:
1. Find collection owned by current user.
2. Find item owned by current user.
3. Reject if either does not exist.
4. Reject or ignore duplicate membership.
5. Add item ID to collection.

Remove item:
1. Confirm collection ownership.
2. Remove item ID from itemIds.

Delete collection:
- Confirm ownership.
- Delete collection.
- Library items remain untouched.

Generator Plan
--------------
The generator is the feature that makes Noreium more than a storage app.

Flow:
1. User selects a collection.
2. User selects target platform.
3. Backend retrieves the collection.
4. Backend retrieves its library items.
5. Backend examines item metadata.
6. Backend extracts the appropriate command.
7. Backend orders commands.
8. Backend builds the final script.
9. Backend returns the script and metadata.

Supported initial platforms:
- Windows
- Linux

Windows command sources:
- winget
- direct installer command if needed later

Linux command sources:
- apt initially
- generic shell command
- distro-specific support later

Generator should skip items with no installation command and report them separately.

Example result concept:
- script
- platform
- included items
- skipped items
- warnings

The generator should not directly query MongoDB. It should use the service/repository layers.

Validation Plan
---------------
Use Zod for request validation.

Validation should cover:
- registration
- login
- library item creation
- library item update

- collection update

- generator requests

Validation should happen before the controller executes business logic.

Error Handling Plan
-------------------
Use one application error class for expected errors.

Typical errors:
- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 409 Conflict
- 422 Unprocessable Entity when useful
- 500 Internal Server Error

Central error middleware converts errors into consistent API responses.

Recommended response shape:

success:
- true/false

data:
- result when successful

message:
- human-readable message

errors:
- validation details when relevant

Do not leak:
- database internals
- stack traces in production
- password hashes
- secret values
- encryption keys

Important Controller Rule
-------------------------
Controllers should remain thin.

A controller should:
1. Read request data.
2. Call a service.
3. Return the result.

A controller should NOT:
- write MongoDB queries
- contain complex business rules
- generate scripts directly
- hash passwords directly
- encrypt secrets directly
- decide ownership rules by itself

Important Service Rule
----------------------
Services contain application behavior.

Examples:
- Verify item ownership.
- Prevent invalid collection membership.
- Generate scripts.
- Coordinate multiple repositories.
- Enforce business rules.

Important Repository Rule
-------------------------
Repositories only handle persistence.

Examples:
- find
- findOne
- create
- update
- delete
- query filters
- populate operations

Repositories should not:
- send HTTP responses
- inspect req/res
- decide user permissions
- generate scripts

MVP Definition
--------------
Noreium MVP is complete when the following works end-to-end:

1. User can register/login.
2. User can create a LibraryItem.
3. User can edit/delete/view their items.
4. User can classify items as TOOL/API/WEBSITE/RESOURCE.
5. User can create a Collection.
6. User can add/remove their LibraryItems from a Collection.
7. User can open a Collection and see its items.
8. User can choose Windows or Linux.
9. Noreium can generate a setup script from that Collection.
10. Another user cannot access or modify the first user's data.

Do not consider the MVP complete just because CRUD works. The generator and ownership security are core parts of the product.

Final Architecture Principle
-----------------------------
Keep the architecture simple but disciplined.

The core should be:

User
  |
  +-- LibraryItems
  |
  +-- Collections
  |
  +-- Generator

Use:

Route
  -> Middleware
  -> Controller
  -> Service
  -> Repository
  -> Model
  -> MongoDB

Do not build the future before the MVP exists.

The first real technical milestone for Noreium is:
authenticated user -> create LibraryItem -> create Collection -> add item -> generate Windows/Linux setup script.
